# Rulegen

A working sketch-to-creative-code studio powered by p5.js and the OpenAI Responses API.

## Run

Use Node.js 22.16+ (Node 24 LTS recommended).

```sh
npm install
npm run dev
```

Create `.env.local` at the project root:

```dotenv
OPENAI_API_KEY=your_key_here
OPENAI_MODEL=your_image_capable_model
```

The app honors `OPENAI_MODEL`. The model must support image input and structured JSON output via the Responses API. Environment files are loaded only by the server. Restart after changing configuration. No API keys enter browser bundles or project exports.

## AI generation logs

Every AI generation (extraction, transformation and state-machine generation, clarification, revision proposals, code, composition prompt drafting and sketch composition, including retries/repairs) is automatically saved on the server under `ai-generations/<UTC date>/<timestamp-intent-unique ID>/`. Each folder contains `log.json` with model, status, timestamps, duration, request ID and token usage when returned; `request.json` with the app input; `prompt.json` with the AI request body; `response.json` (or `response.txt` for non-JSON responses); and `result.json` with the validated result. Code results also include `generated.js`. Input images are saved as `image-*.png/jpg/webp`, referenced by relative filenames in the JSON logs. Failed and cancelled requests include `error.json`; requests interrupted by a server shutdown retain `started` status. A file appears only once its corresponding stage has been reached.

**JSON** in a frame header copies (or downloads) that frame as one JSON document (`rulegen-frame/1`, `app/lib/frame-export.ts`): every node with its semantic transformations (property values with algorithm blocks, and every scalar with its key, range and unit), its base constraint values, its state machine with each state's full constraint values (base merged with that state's changes) and the keys it changes, all transitions, the algorithms used, each brush in the frame with its targeted inspection tools (concern, the annotation in canvas pixels with its styles, summary, overlays, value fixes and recommendations, in this frame's node ids), and the full code as the code panel shows it; sketch strokes, photos and widget code are left out.

**Per-item overlay values.** AI sees drawn-item records with their fields (only bare point lists — `x`, `y`, `t` — are summarized as a box); an `each` overlay's label that does not read its item is shown once, not repeated on every item; the inspect prompt asks labels to state the item's own value at that step (never a property's range or thresholds), and the code contract asks each drawn item's record to carry the values that made it differ (e.g. `{ x, y, w, h, speed, tips }`). When existing code computes such a value but does not keep it on the records, the inspection returns `records` (edits that only add those fields where the record is pushed; validated on the server) and it is applied with the result, in place like an accepted hidden parameter (ITEM RECORDS in the panel, Undo apply). At a held step the overlays read the stores as the running code draws that step now (the iframe reports them with the restore id), so steps recorded before still show the new fields; a label with a part that cannot be read is hidden instead of showing "?".

**Hidden parameters.** A targeted inspection also reads the brush's module code and may suggest exposing a constant the concern depends on (a ratio inside an algorithm, a jitter amount, a fixed count) as a new property (`parameters`: node, existing transformation, property with the constant's current value and a range, a reason, and exact edits replacing the constant with `m.v("<node>/<property>")`; the server keeps only edits that apply once and parse). **Accept** adds the property to every stamp drawn by that module in the frame and patches the module without regenerating: the new program is prepared, the module is swapped into the running result in place (`rulegenRefreshModule` keeps `m.store`, so nothing drawn is lost), and scene and code are one Undo apply entry; the card then shows a slider to adjust it. **Reject** folds the card (kept with the tool, can be brought back). `m.memo` entries also record the values read while computing, so changing such a value recomputes them.

Open **AI history** in the header to browse every generation, inspect successful results or errors, download the result log, and restore a completed generation without another AI call. New generations also save `context.json` (the project before generation, target sketch, selection region and annotation draft) and `recovery.json` (the restorable project plus clarification/proposal data) alongside image assets. Restore replaces the current local draft with that generation's project; export any draft you want to keep first. Unconfirmed revision proposals restore for review rather than being applied automatically. The board comes back as it was: frame positions (proxy frames included) and the view (camera and zoom); only a log without a saved view moves the view to the restored frame. Logs from previous project formats are not restored.

Transient OpenAI failures (503 overload, 500/502/504, rate-limit 429) are retried up to 3 times with backoff (2s, 4s, 8s, or the server's Retry-After); exhausted quota and key/model errors are not. Retried responses are kept as `response-<round>-retry<n>.txt` and listed under `retries` in `log.json`.

**Error logs.** Every error the studio shows is also written to `error-logs/<UTC date>/<timestamp-source-id>.json`: `ai` (failed generations with intent, model, HTTP status, provider error code and the `ai-generations/` key), `prepare` (code that failed the safety check, with the code), `runtime` (errors thrown by a generated sketch in the browser, with its program), `ui` (other errors shown on a frame) and `server` (malformed requests). API keys are redacted and image data URLs omitted. Set `RULEGEN_ERROR_LOG_DIR` to change the folder; it is excluded from Git.

Logs are local files excluded from Git, and do not include authorization headers or API keys. They are retained until you remove them. Set `RULEGEN_AI_LOG_DIR` in `.env.local` to change the destination (relative paths resolve from the project root). If the server cannot write logs, generation reports a storage error. Local actions such as Make pen, widget edits and running existing code do not invoke AI and do not create generation logs.

## Workflow

1. Use **Add sketch frame (+)** in the left toolbar to add an independent sketch canvas. Click/draw on a frame to edit it; Undo, Redo and Clear apply to that frame. Use its Extract button to find collections and objects there. Use the trash button in each frame header to delete it. Deleting a sketch also removes its generated result, panel and drawing history; deleting an extracted frame keeps its source sketch. The original sketch can also be deleted; Add sketch frame restores an empty sketch when needed. Deleting the brush playground clears its test marks and closes the Brush step; opening Brush shows it again. Frame deletions persist in local saves and JSON exports. Additional frames, artwork and positions are included in local saves and JSON exports. Draw with the pencil, erase, undo/redo, pan with H or Alt+drag, and zoom using the left toolbar. Pencil settings open beside the pencil button.
2. Attach a PNG, JPG, or WebP photo (up to 20 MB), drop it on the canvas, or paste a copied image/screenshot with Cmd+V / Ctrl+V while outside text fields. Photos are resized locally before use and pasted/attached into the selected sketch frame. Click a sketch frame, its header, or its Focus button to select it; a green border and highlighted title show the active destination. Pasting can be undone/redone independently in that frame. You can sketch over a photo.
3. **Extract** the whole image, or draw a closed lasso with L to extract only that region, into a new frame beside it. The AI returns a scene of **collections** (groups that carry a semantic transformation applied to all members) and **objects** (basic primitives), nested as needed, plus a reusable **algorithm library**.
4. Use the **Layers** panel (left of the canvas) or the **Select** tool (V) on the sketch to select, rename, hide, group (⌘G), ungroup (⇧⌘G), nest (drag in Layers), reorder, move (drag / arrow keys) or delete nodes. Clicking selects the outer collection first, clicking again goes one level deeper. Layer edits have their own Undo/Redo.
5. The right panel (no tabs) shows the selected node's **stack of semantic transformations** (up to 6 per node, applied top to bottom; add one blank or with AI, rename, reorder with ↑↓, regenerate or delete each). Property ids are unique per node, so live keys stay `nodeId/propertyId`. Each property is a **socket** (spatial, stylistic or temporal) holding a value or an **algorithm block**. Blocks are independent of properties: drag one from the **block palette** (or from another socket) into any number/block socket, right-click a block to **Copy block** and right-click any socket to **Paste** it (the clipboard works across sketches), swap a socket's block from its menu, or drop a block on the empty socket to add a property. Block arguments are sockets too, so blocks nest. Editing a block's definition in the palette updates every place it is plugged in. Regenerate one property or the whole transformation with AI. Drag a layer from **Layers** onto another frame to copy it there with its members, blocks and machines: the result is generated and drawn inside that frame. Moving nodes within a frame moves the running result with them, live while you drag.
6. Generate p5.js code from the scene. Every scalar (including nested algorithm arguments) and each node's position, size and visibility are linked, so sliders and layer moves update the result without another AI call. Code shows in the bottom **Raw p5.js** panel: edit and run it there, copy or download it, or ask AI to fix a runtime error.
7. Click **Annotate** above the generated result and sketch freely over it. Click **AI clarification 만들기** to let AI compare the clean result with your sketch and fill an editable **Text clarification** draft. Review or edit the draft, then request rule/visual-feature suggestions. Use **AI 설명 다시 만들기** to reinterpret an updated sketch. Review concrete Before/After changes to collections, objects, properties and algorithms, then **Confirm** to regenerate connected p5.js code and apply them together. Use **Erase** (or E), **Undo/Redo**, Cmd/Ctrl+Z, Cmd/Ctrl+Shift+Z or Ctrl+Y to edit the sketch; Clear preserves the underlying generated result and clarification. Editing the sketch or clarification invalidates older suggestions. Cancel or generation failure keeps the current result. Feedback sketches are temporary; confirmed changes persist with the project.
8. Right-click a block (or use the palette) and choose **Make pen** to add a colored pencil carrying the algorithm call, its exact arguments and every definition it depends on. This is immediate and does not call AI. Draw freely with it just as with Pencil: the canvas keeps ordinary lines, each tagged with the pen's semantic meaning. Switch between pens and Pencil to sketch a composition. Compose first builds a collection scene that reuses the pens' algorithms by id, then generates its code. Click **Compose sketch** with an empty **Compose prompt** to have AI recognize the full sketch and fill an editable Korean prompt first. Review or edit it, then click **Compose sketch** again to generate the result. **AI prompt 만들기 / AI prompt 다시 만들기** can also draft or refresh the prompt, taking existing text into account. Prompt drafting needs no prior feature analysis and uses the image plus stored stroke semantics; edits made during a request are preserved. Drafting is logged alongside other AI requests. AI receives the full sketch image, ordered paths (including erasers), per-stroke algorithm snapshots and the prompt to create the selected sketch's generated result. Pen colors identify semantics; the prompt and drawn forms determine the output. For example, sketch an increasing pattern with a Power pen and ask for growth using its exponent along a Pencil layout. Click a toolbar pen to inspect or edit its meaning and color; changes affect future strokes. Removing a pen keeps the semantics on existing marks. Pens, stroke metadata and each sketch's Compose prompt persist in project JSON and local storage.

The current exploration, uploaded image, scenes, blocks and generated code persist in browser local storage (project format `version: 2`; earlier formats are not migrated). Export a `.rulegen.json` file before starting a new project to keep an independent copy. Imported JSON is validated. Storage quota failures are shown in the header; JSON export is still available.

Generated sketches run in an iframe with a separate sandbox, no app storage access, and no network permission. Code is parsed on the server and guarded against unbounded loops and recursion: a frame (or input event, message) still running after 10 s stops with an error (`app/lib/render-guard.ts`). The engine and p5 library are bundled locally; no CDN is required. Rendering errors are surfaced with an AI repair option.

## Verification

```sh
npm run typecheck
npm test
npm run build
npm start
```

Tests cover code execution guards, forbidden APIs, semantic pencil snapshots, prompt composition context, procedural-economy review and repair, semantic composition AI context, image request validation, and project serialization. Live API requests incur usage on the configured OpenAI account; no mock outputs are returned.

**One frame model.** There are no separate result frames: every frame is a sketch frame that renders its own generated result underneath its strokes and layer boxes, and you can keep sketching on it. **Extract** and **Compose** place the scene in a *new* frame beside the source sketch and render its result there; the source stays a plain sketch, and the new frame remembers where it came from (it warns when the source changes). Frame headers offer **Run/Pause** (animations and state machines), **Re-render**, **Generate/Update**, **Annotate** and **Extract**. Interaction is part of the **Brush** tool (there is no Interact button): with a brush's Brush tool on the active frame that has that brush, only the running result takes mouse, touch and keyboard input, while the frame's strokes, layer boxes, layer drops, scene shortcuts and image paste are switched off (pick another tool or press Esc to stop). The compose-prompt and compose prompts treat a form redrawn in another shape (pressed, hovered, dragged, before→after) as one node whose look changes with the interaction, not as extra collections. Value-only changes (sliders, layer moves, state values, timings) are pushed into the running sandbox and re-rendered in place; only program changes reload it, keeping the last image on screen meanwhile. Each frame keeps its own scene, selection, code draft, prompts and result in local storage and project JSON.


The toolbar includes a default **Interaction pen**, alongside algorithm pens. Use it to sketch click/tap targets, hover areas, drag directions and drop locations. Select it again to edit its meaning and color. Marks retain the meaning they had when drawn; the default pen and annotations persist in local storage, project exports and AI recovery snapshots. AI interprets them as user input annotations and generates actual p5 input callbacks, excluding the guide marks from the artwork. Compose prompt drafting, state planning and code generation all receive the annotated sketch and ordered stroke metadata.

State machines belong to individual **collections and objects**, not to the whole frame. Use **Generate state machine** on a node without one; each state changes only that node's property values (same structure as the base property). The bottom **State Machine** panel shows the selected node's graph with semantic transition labels, play/pause/restart and event buttons. Clicking a state jumps the preview there and switches the right **Properties** panel to that node with the state's values: slider edits then apply to that state only (**Base** edits the shared values), and the state's description and outgoing transitions are edited there too. Several nodes' machines run independently; generated code reads `rulegenState["node id"]` and emits `rulegenEmit("node id", "transition id")`; the prompts require both ids as string literals at every direct call (no wrapper helper or variable id), because the server checks them against the scene. Planning still separates meaningful input, motion, completion, cancellation and recovery phases, with up to **32 states and 128 transitions** per node. In the panel, drag the empty background or scroll to **pan** (double-click resets). Drag state boxes and transition labels to **move** them (a moved label bends its arrow to pass through it) (saved per frame and node; **Auto layout** restores the grid). Click a state or transition to **select** it, click the background to deselect; **Refine state / transition / machine** then opens a text box instead of running at once, showing the attached item as a chip (× detaches it to refine the whole machine). **Annotate** lets you draw on the graph; the strokes are attached too, and Refine sends the graph image (attached item in orange, annotation in coral) plus the items each stroke touches. The AI changes only what the request needs (`machine-refine` intent, `prompts/machine-refine.md`) and also rewrites the frame's **Compose prompt** bullets to describe the refined behavior; the source sketch's prompt follows when it is the same prompt.

## Prompts

All AI prompts live in [`prompts/`](prompts/) as Markdown, one file per intent (`extract`, `compose`, `transform`, `state-machine`, `machine-refine`, `inspect`, `handles`, `code`, `compose-prompt`, `clarification`, `revision`), with shared contracts in `prompts/contracts/` pulled in through `{{include:…}}`. Each file ends with its output JSON format, and `prompts/schemas/<intent>.json` holds the exact strict JSON Schema the server sends. Prompts are re-read on every request, so edits apply without a restart. After changing a schema run `npm run prompts:schemas` (tests fail when the files are stale). `RULEGEN_PROMPT_DIR` changes the location.

**Structure and granularity.** Parts that share a clear common feature (same primitive, look or behavior) stay ONE whole object, their differences expressed as fine-grained transformations; only parts that differ in kind become nested collections (whole → part groups → parts, up to 5 levels; deeper model output is flattened to level 5 and layer edits beyond it are refused). Transformations are split as finely as possible: each is ONE semantic operation named for what it does ("Radial bloom", "Petal size falloff", "Wind sway"), usually 1–3 properties, never an effect-type bucket like "Spatial" / "Style" / "Temporal" (up to 12 per node). These rules are given to the model through the prompts only; the server does not check them (the former checks are kept in `backup/server-checks/`).

**Brushes (Brush Stamps) and inspection.** Collections are shown as **Brush Stamps**. Generated code is one independent module per root node: `rulegenModule("<root id>", function (m) { … return { setup, draw, mousePressed, … } })`, reading only its own nodes through `m.v`, `m.box`, `m.state` and `m.emit` and keeping its changing state in `m.store`, while the host owns the canvas, the loop and input. Every root collection that Extract or Compose creates becomes a **brush tool group** in the toolbar. Click a group to select its tool; click the selected group again to open (and again to close) its tool panel, which keeps a fixed height and scrolls; the group icon follows the last chosen tool. The **Brush** tool adds the brush to a frame that does not have it yet (one copy where the gesture starts, with its code module, run immediately with no AI) and feeds the gesture to it as mouse input; on a frame that already has it, it never adds another copy but plays with it (interaction). The Brush tool draws no gesture path or layer boxes. On a frame whose result is running, the prepared module is injected into the running sketch in place (no reload, nothing reset), and the program with the brush is prepared ahead while the tool hovers a frame, so even the first gesture reacts at once (input that had to wait is fed over a few frames; while it is fed the result is shown and focused, so sketches that check p5 `focused` react from the first drag). **Delete stamp / Delete master** in the brush banner (or Layers' trash, Delete key) removes a whole brush stamp; adding or removing whole module roots, and undoing that, keeps the frame's code live. Dragging a root layer to another frame copies it the same way. A brush's **master** is its collection in the source frame; every copy is an **instance** (◆/◇ badges in Layers, a banner in the right panel, the master's frame in the group panel). Plain value adjustments (sliders, inspection value fixes) apply to an instance directly; changing an instance's semantic transformations themselves or its state machine (including those inspection recommendations) first asks: **Detach and create new brush** (the instance becomes the master of a new brush, keeping the targeted tools, then the change applies), edit the master, or cancel; when the master's frame is gone the instance can be made the master. **Inspection** records up to 20 steps automatically (one per state change of that brush; while the Brush tool plays on a frame every brush in it records; a frame picker inspects the brush in any frame that has it; Inspection has its own pane beside Code / State Machine, and the graph highlights the inspected step's state and transition plus the states/transitions the inspection is about). Each step keeps the runtime state (every module's `m.store`, machine states, random seed), so selecting a step on the timeline puts the running result back at that moment, and value edits redraw from there. **Inspection annotation** marks a concern on the frame. Each **Create targeted inspection** adds a new **Targeted inspection** tool for that concern to the group (`inspect` intent): overlays computed from each step's values, value fixes and recommendations. When no existing transformation is related, a recommendation can instead add a new one (`add-transformation`, **Add with AI**); once applied it reads as the transformation it added (stored as `addedId`, back to a new one if undone), and the tool's overlays, summary and value fixes are rebuilt by AI for the result with it (`inspection.update`), keeping the recommendation list. A transformation recommendation can change several transformations of a node (`targetIds`): one chip each, and Apply with AI regenerates them in turn and rewrites the code once. **Undo apply / Redo** next to the recommendations undoes or redoes a whole applied recommendation (scene, code rewritten after it, and prompt together); **Autocomplete** under the concern box asks AI to read the inspection annotation (and what has been typed) and suggest concerns (`concern` intent, only when pressed: up to three; the best one shows as the placeholder or as a grey completion of the typed text, taken with Tab, or pick one below); the inspection annotation keeps up to 128 strokes (the oldest go first); its pen has its own **color, width and opacity** (remembered in the browser, stored with each mark and with the targeted tool, and sent to the AI in the annotated image and as `annotationMarkStyles`), and the inspection annotation has a **Pen / Eraser** toggle (also the toolbar Eraser / E while that tool is in use) to rub out single marks on the frame. A targeted tool works on the master and every instance: its result is stored in the brush's shared node ids (`codeId`) and translated to each frame's ids when shown (overlays on every copy in the frame, fixes for the selected one). Clicking an overlay highlights what it shows. Overlays sit on what they show: a list of points in `m.store` (an outline, a path) reads as its box (`@x`, `@y`, `@w`, `@h`, `@cx`, `@cy`, `@n`, e.g. `item("@cx")`), the recorded input is the pseudo root `"@input"`, and the AI gets each drawn item's box instead of truncated point lists, so it can place overlays on the items rather than at fixed spots. A targeted inspection is a reusable tool for its concern, not an answer about one picture: the marks only point at an example, and the overlays are drawn for every item the concern is about (`each`), at every step, with any values and on every stamp, never from the marks' coordinates, a fixed item index or what the current image shows.

**Create Minimal Example.** Every semantic transformation card has a **Create Minimal Example** button. The example also becomes a **sub brush** inside the tool group of the brush the transformation belongs to (SUB BRUSHES in the group panel, each with its Brush and Inspection tools), so it can be brushed onto frames and played with right away. It adds an ordinary sketch frame beside the current one holding just one collection and one object with only that transformation (a collection's transformation acts on one plain member object; an object's transformation sits on the object inside a plain collection), without state machines and with only the algorithms it uses, then renders it so the transformation can be tried and its sliders tested on their own.

**Runaway guard.** Every loop and function of generated sketch code and widget code calls a guard that stops a frame only when it has run for more than 10 seconds (an endless loop or recursion); the clock restarts every frame, input event and message, so heavy but finite frames (e.g. long trails redrawn from `m.history()`) are not stopped (`app/lib/render-guard.ts`). A frame's cost should not grow with all the input given: each gesture of `m.history()` has a stable `id` and a `rev` that changes with its points, and `m.memo(key, () => value)` is a host cache (outside `m.store`, unused entries dropped) so modules compute what each gesture makes once per id, rev and values; the code contract requires this, forbids keying on the whole history, and keeps `m.store` to state and a light list of drawn items.

**Direct manipulation handles and proxy frames.** Each property can get its own direct manipulation interface, built for what that property means: the `handles` intent has the model write a small p5 widget per property (`rulegenHandle(function (h) { return { draw, pressed, dragged, released } })`) that draws a simplified miniature of the property's effect, computed from its current values, and lets the user grab part of it. For example, dragging a branch fork's arm sets the branch angle, rotating petals sets their count, and dragging a wave's crest sets the amplitude; several arguments of an algorithm property can share one 2-D gesture. The model sees the property's meaning, its transformation, its scalars (paths, ranges, units, options), the algorithms behind it and the current result. Widgets run in a **proxy frame**: a separate frame beside the target frame, one per node, showing its widgets in a grid inside a sandboxed iframe. Using a widget sets the node's values in the target frame live (the selected state's values when a state is being edited), and outside changes redraw the widgets. Widgets read values with `h.v`/`h.spec`/`h.ratio` and write them with `h.set`/`h.setRatio`, which clamp to the scalar's range, round to its step, and only reach the paths the widget declared. Widgets are designed for one property (◎ on a property card) or one transformation (**Design with AI** on a transformation card, or a transformation's **Design** button in an empty proxy frame), never the whole node at once; the proxy frame opens on its own. On the card's PROXY HANDLE row you can edit the hint, **Redesign** with an instruction, view the widget code or remove it. A widget that fails at runtime blanks only its own cell and offers **Fix with AI** (the error goes with the request). Widget code is guarded like sketch code (no browser globals, timers or eval, bounded loops, no canvas or `p.setup`/`p.draw`) and stored prepared. Handles are UI only: no code regeneration, never sent with the scene to other intents, allowed on brush instances, and kept across property regeneration and revisions while their scalars exist. Proxy frames are saved with the project (`proxyFrames`) and go away with their target frame. A layer over each widget of the proxy's sandboxed iframe receives the pointer and forwards it in, so input never depends on the iframe being hit; the rest of the proxy body (each cell's title strip, the gaps between cells, or all of an empty proxy frame) drags the frame on the board like its header. The relation is always visible:
- The proxy header shows **LINKED → frame / node** (and the edited state).
- The target's header shows **◎ node proxy** for each proxy that controls it.
- A dashed arrow on the board joins the two frames.
- Hovering either chip highlights the other frame, and clicking it goes there.

Value changes reach the running result without wiping it: a module's `setup` runs again only when a value it read (`m.v`/`m.box`) changed, so trails, particles and drag state survive tweaking. Modules also get the input given so far, `m.history()`: the last 24 press-drag-release gestures, in canvas pixels. Under the code contract's DERIVE FROM THE INPUT rule, anything made from input (trails, stamps, strokes, emitted items) is recomputed in `draw` from that history and the current values, never stored with the values of the moment it arrived. Changing a value then adjusts what is already drawn in place: no redraw from scratch, machine states and the rest of the store unchanged. The history is part of inspection snapshots. Fallback for older code: when a module takes input but does not use `m.history()`, a value change starts over and replays the recorded input quickly with the new values, and the proxy frame offers **Update code to adjust in place**. Saved programs are brought up to date with the current host runtime on load (`refreshProgram`).

**Procedural economy.** Extraction, Compose and revisions describe repeated elements (petals, dots, leaves, rows, scattered marks …) as ONE node whose semantic transformation generates the instances: a count, a layout block (row/grid/radial/scatter/along-path/recursive) and algorithmic per-instance variation. Generated code draws every instance inside the node's box.
