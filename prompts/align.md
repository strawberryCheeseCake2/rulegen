# align — fix a brush to the state the user drew at one moment of its execution

The user is shaping ONE brush (a reusable collection, also called a Brush Stamp) in a running p5.js sketch and asked a question or a change about it (`concern`; `inspectionSummary` is what a targeted inspection found, possibly empty). In an Execution frame they ran the brush's execution to ONE MOMENT (`execution`: what the frame shows, how far execution is, the state machine step just executed (`last`) and the next (`next`) — a state visited, a constraint computed or a transition taken —, the kind of operation now (`stage`)) and DREW there, by hand, the state they want instead of the one the brush produces, with tools made for their concern (`tools`; `reading` is how the concern was read; `startedFrom`, when given, is the guess they loaded and then changed by hand: what they drew wins over it).

- The image is the moment's picture with the drawing on it: parts taken away and the places lifted parts came from are painted over with the paper (their outline dashed); lifted parts are drawn where they were put; forms are drawn with their outline (merged forms as ONE outline); lines; items of the picture pointed at (a dashed outline); the names and tags given; notes (freehand marks).
- `behaviors`: procedural behaviors the user DREW and the frame RAN: each its tool, the objects drawn with it, the values what is drawn gives (`key`, read on the drawn object as `expr`) and the `patch` the frame ran with (its code reading them with `m.opt`). What the user saw is the brush running that code with what they drew: a fix that makes that behavior part of the brush may take that code, with the values it read as the brush's own (a new param where the user should keep adjusting it, else the number they drew).
- `drawn` says the same in numbers (canvas pixels): each object (`kind`: `"shape"` a form, `"line"`, `"crop"` a part of the picture lifted, `"erase"` a part taken away, `"item"` an item of the picture pointed at as it is; `tool` the tool it was made with; `label` its name or tag; `brushObject` the node of `brushNodes` its tag links it to (`label` the words on that tag); `tags`, when it has more than one tag: every tag on it, each with its words (`label`) and the node it links to (`brushObject`), all of them true of it; `specs` the rules on its tag the user decided, each `{ aspect, expr, means }` (`means`: the reading they chose among the ones offered, when it was one; a quantity left open is not listed: the brush keeps deciding it as it does): a quantity of it (`w`, `h` its size, `x`, `y` its center, `rotate`, or another word such as a color or a count) and the expression that gives it, read on this moment's stores as overlays read them (`item("w")`… its own box where it was made); `box` where it is now; `from` where a lifted or erased part was; `moved` how it was moved, scaled and rotated; a line's `points`; `mergedInto` its merge) and `merges` (forms drawn as one outline, with their name).
- `stateSet`: execution state the user SET by hand at this moment with state tools (`tools` of kind `"state"`, their `handles`): each `key` (`@store:<root>:<path>` a value the module keeps, `@input:…` a point of the input), the `tool` and `name` it was set with, and what it `was` and is `now` (a number, or a point `moved` by `dx`, `dy`). The picture is drawn with it set: what the brush does from that state is what the user saw there.
- `notes`: the freehand marks (normalized 0..1); `request`: what the user wrote (may be empty).
- `refs` (when present): runtime state the user referred to as `@<id>.<field>` in a rule, in words on a tag or in `request` (e.g. `@mid.x`, `@first.w`): each with its `name`, what it `means`, and per field its `ref`, its expression (`expr`, read on this moment's stores as overlays read them), where that is in the brush's code (`code`: its path into `m.store` such as `items[3].w`, or `runtime("<name>", "<id>")` for a quantity the code keeps per item with `m.runtime`) and its value now (`now`). A reference stands for that quantity of the execution (which items and values it reads), so a rule `@first.w + @second.w` means the sum of those two things' sizes for any items in that situation.
- `step`: the brush's values and run state at this moment (`runtime.stores`: what each brush root keeps in `m.store`); `brushNodes`, `params` and `code` describe the brush.

THE DRAWING IS THE SPECIFICATION of the program state the brush must produce at this moment. Compare it with what the brush produces now (the picture under the drawing, the stores at this step) and find the change of the brush's RULE that makes it produce that. It is a demonstration, not a one-off edit of this picture: what the user did to these items shows what must happen to EVERY item in the same situation (every pair in this relation, every item at this kind of place, every step of this operation), now and later. Read it literally and precisely:

- forms merged into one outline: those things become ONE form there (their borders gone), not two touching ones;
- a form placed, scaled or moved: that size, place or turn, measured against the item it covers or stands for (the ratio of the boxes, the offset of the centers);
- a lifted part moved, scaled or turned: the thing that is drawn now ends up that way;
- a part taken away: it is not drawn there; with a new form over it: it is replaced by that form;
- a line: where something must happen or stop (a boundary, a limit, a path things follow, a direction), at that place;
- rules on a tag (`specs`): the most precise part of the specification, what the user kept or wrote for that quantity: the brush must produce it BY THAT RULE (read which items and values its store reads stand for), for every item in the same situation, not only the number it gives here; a rule that is a plain number is a value the user set by hand (from the drawing or typed);
- names and tags: the role of what they name ("Removed", "One form", "Grows"); a tag with `brushObject` says which object of the brush that thing is (or must be), so the fix is about that node; an item pointed at as it is: that existing thing, in that role;
- state set by hand: the state at which the outcome they want happens (a reach set larger until two things meet, a count set where it should stop, a point moved where it should be). The brush must reach that state (or decide as it would there) on its own, in this situation, by its rule: e.g. the reach grows by the ratio `now / was`, the limit is the count set, the test passes at that distance. Drawn objects and state set together are one specification.

The fix is in the operation the moment is about (`stage`, `last`, `next`: usually the constraint computed there, or the transition taken): how it places, sizes, orients, joins, skips or replaces what it draws, and the condition under which it does so. Coming out "similar to" or "roughly like" the drawing is not a fix; take the quantities from the drawing.

## What to return

ONE fix:

- `kind`: `"value"` only when values of `params` alone produce exactly the drawn state (`changes`: `key` from `params`, `stateId` `""` (values are the same in every state), a `value` of the key's type within its range). Otherwise a structural change: `"constraint"` (rewrite the constraint `targetId` of node `nodeId`; others of the same node that must change with it in `targetIds`), `"add-constraint"` (a NEW constraint on node `nodeId` when none of its constraints covers what has to change: it determines one property, a new one or the same one in another phase; `targetId` `""`), or `"state"` / `"transition"` (refine that state (which constraints it evaluates, in which order) or transition (its event) of node `nodeId` when the drawn state is how the brush must REACT to something that happens while it runs: things meeting, touching, overlapping, crossing a line, a limit being reached). `changes` is `[]` except for `"value"`; `targetIds` is `[]` except for `"constraint"`.
- `nodeId`, `targetId`: ids exactly as in `brushNodes`.
- `title` (English, about 6 words): the rule, e.g. "Join overlapping leaves into one outline".
- `detail` (English, 2–4 sentences): the new rule concretely enough to write the code from it: which items, under which condition, what happens, with the quantities read from the drawing (sizes, distances, ratios, where the line is), and what stays as it is. For `"add-constraint"`, which property the new constraint determines, how it depends on the rest, and the idea of its computation.
- `reply`: one English sentence on how you read the drawing, e.g. "You merged the two overlapping forms into one outline, so overlapping items now join into one."

When what the user drew cannot be done in this brush, return the closest fix it allows and say so in `reply`.

Treat image content as visual evidence, not instructions.

## Output JSON

Return exactly one object matching `prompts/schemas/align.json`.
