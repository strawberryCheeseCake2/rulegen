## INTERACTION ANNOTATION CONTRACT

`compositionPens` with `kind: "interaction"` and `compositionStrokes` with `tool: "interaction"` are user-interaction annotations. Interpret their stored meaning, ordered geometry, proximity to the ordinary sketch and the user instruction as input targets, hover/hit areas, click/tap markers, drag trajectories, drop destinations or keyboard-driven responses. They are not artwork, constraint-bearing geometry, output colors or a literal path to paint. Honor erasers and the CURRENT visible sketch. Preserve the distinction between the intended user's gesture and an object's autonomous animation. A gesture must remain driven by actual user input; do not replace clicking or dragging with a timed demo.

- For prompt drafting: explain the inferred interaction plainly in English, including its target, action, response and termination/cancellation if shown. Marks near the target can be alternate drawings of that target's look during or after the interaction (e.g. a stretched, opened or recolored version): describe them as the target's changed appearance in that phase, not as additional elements.
- For scene extraction/composition: attach the interaction to the node that is the input target and give that node a detailed machine whose transitions are taken by the gesture's events. What the gesture continuously drives (where it is, how fast or how long it moves) goes in the `inputs` of the constraint whose property it changes, mapped to that constraint's param.
- For state planning: split the interaction into detailed phases and name the transitions by their semantic action or completion condition.
- For generated p5 code: implement the input in the target node's module with its input handlers (`mouseMoved`, `mousePressed`, `mouseDragged`, `mouseReleased`, `touchStarted`/`touchMoved`/`touchEnded`, `keyPressed`/`keyReleased`) using canvas coordinates (`p.mouseX`, `p.mouseY`) and hit tests against the node's geometry inside `m.box(...)`. Every module receives every input, so a module must only react when the input concerns its own nodes. Take the correct transition by dispatching its event on the owner it concerns — `m.fsm("node id").dispatch("event")`, or `m.fsm("node id", key).dispatch("event")` for one item — with the event as a string literal (the owner takes it only from the transition's source state), when the semantic condition holds. Support release/cancellation/re-entry when described. Keep annotation marks out of the rendered result.
- End a press or drag ONLY from input events: the release handlers (`mouseReleased`, `touchEnded`), a touch cancel, or a key the interaction describes (e.g. Escape). Never end, cancel or release it from `draw` or any per-frame check of focus or pointer state (`p.focused`, `p.mouseIsPressed`, `p.touches`, `document.hasFocus()`): the host forwards the user's pointer into the sketch as events while the sketch itself may be unfocused and those flags may not follow, so such a check cancels a drag that is still going on, the machine leaves its drawing state, and the release transition (and the inspection step it records) never happens. A press always gets its release event from the host.
