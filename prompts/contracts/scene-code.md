## SCENE CODE CONTRACT

Your code is a set of independent MODULES, one per ROOT node (a node whose `parentId` is null; `modules` lists each root id with the node ids it draws). A module is drawn on its own: the user can lift one into another sketch as a reusable brush stamp, copy it several times, and every copy runs the same module code with its own node ids. So the WHOLE program is only this, once per root, in any order:

```js
rulegenModule("<root id>", function (m) {
  // only functions and constants here: helpers, fixed numbers
  function decayed(base, ratio, depth) { return base * Math.pow(ratio, depth); }
  const GRAVITY = 0.4;
  return {
    setup() { /* optional: (re)build m.store, e.g. m.store.particles = []; runs again ONLY when a value it read with m.v / m.box changes */ },
    draw() { /* required: draw this root and all of its nodes, every frame */ },
    mousePressed(event) { /* optional input: mouseMoved, mouseDragged, mouseReleased, mouseClicked, doubleClicked, mouseWheel, keyPressed, keyReleased, keyTyped, touchStarted, touchMoved, touchEnded */ },
    stateEntered(nodeId, stateId, key) { /* optional: an owner of this module entered a state */ },
    // required: one named compute function per constraint of every node of this module
    constraints: { "<node id>": { "<constraint id>": computeSomething, … }, … },
  };
});
```

### FSMs and constraints in code

Each node (collection or object) of the module has an FSM, declared in the scene (`machine`; a node without one is a single implicit state evaluating all its constraints in declared order). The host runs it; the code drives it:

- `m.fsm("<node id>")` — the OWNER of that node's FSM: the node itself. `m.fsm("<node id>", key)` — the owner of ONE of the many items the node draws (`key`: a stable item id such as `` `${g.id}:${i}` `` or the item's index), with its own current state and data, sharing the node's FSM definition. An owner has:
  - `owner.state` — its current state id; `owner.data` — the properties its constraints computed, by property name (`owner.data.position`, `owner.data.size`…); `owner.key`.
  - `owner.evaluate(...inputs)` — computes the current state's constraints IN THE STATE'S ORDER: for each one the host calls its compute function as `compute(owner, ...inputs)` and immediately stores the returned value in `owner.data[<property>]` before the next constraint runs; returns `owner.data`. Call it where those relationships apply (each frame in `draw`, for every item, or in an input handler), then draw from `owner.data`.
  - `owner.dispatch("<event>")` — takes the transition declared for that event from the owner's current state (none: nothing happens). Call it exactly when the event happens (a hit, a release, contact, completion, an absorption), so the declared transition is taken before any resulting removal. The event is a STRING LITERAL at every call site, one of the events declared by this module's nodes' transitions, and EVERY declared event must be dispatched somewhere.
  - `owner.remove()` — forgets an item's owner (when the item is gone for good).
- `m.owners("<node id>")` — the owners of that node that exist now (the node's own and its items'), e.g. for a collection's constraint that relates its members.
- `constraints` (returned by the module) — for EVERY node of the module and EVERY one of its constraints, the compute function, keyed by node id and constraint id: `constraints: { petals: { positions: computePetalPositions, size: computePetalSize }, petal: { shape: computePetalShape } }`. Write each as a NAMED function declared in the module (`function computePetalSize(owner, index, count) { … }`). It receives the owner and the inputs given to `evaluate`, reads its params with `m.v` (and other owners' data, boxes, the input), keeps its neighbor lookups, contact tests and intermediate calculations as LOCAL variables inside it, and RETURNS the property's value. It does not draw and does not dispatch.
- Evaluate every node that has constraints (each item's owner for a node that draws many). Keep drawing operations that are not relationships in ordinary code, reading the evaluated `owner.data`.
- The host records every evaluation as state machine steps (the state visited, then each constraint computed with its value and the params it read) and every transition taken, so the user can step through them. So compute a property ONLY in its constraint's function, and branch on `owner.state` only where the drawing itself differs between states.

Nothing may be written outside the `rulegenModule(...)` calls, and modules must not share anything: no top-level variables or functions, no undeclared globals. The factory parameter must be named `m` and is used ONLY as below (call these directly with string-literal arguments, never pass `m` or its functions around):

- `m.v("<key>")` — a live value of a param. For EVERY entry of `parameterBindings` whose node belongs to this module, read it with the EXACT literal key, inside the compute function of the constraint that holds the param, and use it in the property it computes so that moving the slider changes the visual. Keys are exactly `nodeId/paramId`. Never copy current values as literals and never build keys dynamically. `m.v` takes exactly one argument.
- `m.box("<node id>")` — `{ x, y, w, h, visible }`: the node's current box in canvas pixels. Place EVERY node of the module inside its box (translate/scale your drawing into it) and skip nodes that are not `visible`, so that moving, copying or hiding a node follows live. Never hardcode positions.
- `m.history()` — the input given so far: an array of gestures (each press → drag → release on the canvas, oldest first, up to 24), each `{ id, rev, points: [{ x, y, t }], done }` in canvas pixels with `t` = ms since its press; `done` is false while it is still held. `id` never changes and is never reused; `rev` changes whenever that gesture changes (a new point, release, or its points being thinned), so a gesture with the same `id` and `rev` has exactly the same points. Read-only: never change it. Hover moves without a press are not in it.
- `m.memo(key, () => value)` — returns the value computed for `key` (a short string or a small array), computing it only the first time. It is the module's cache for what is derived from the input: kept by the host (not in `m.store`, so it is not copied into every saved step), and entries not used for a few seconds are dropped. Build the key from what the value depends on: gesture `id`s and `rev`s and the values it uses, e.g. `m.memo(["trail", g.id, g.rev, spacing, size], () => layOut(g, spacing, size))`. Data that is not a gesture (a preview, a sample path, a layout the code makes itself) has no `id`/`rev`: key it by what makes it — its index and the values and seed it is computed from (e.g. `["preview", i, count, spacing, seed]`), never by its points or a string made from them. Never put points, `m.history()` or other large data in a key, and never `JSON.stringify` the history.
- `m.demo("<id>")` — ONLY when the instruction gives demonstration values by id: the value the user is showing live with a direct manipulation tool (any JSON: a number, a color, an object or list), or `null` while nothing is shown. Read it with the literal id, where the instruction says it acts, and behave as before while it is `null`. Never use it otherwise.
- `m.p` (or `p`) — the shared p5 instance to draw with.
- `m.store` — this instance's state object. Everything that changes between frames or after input and is not an owner's state or computed property (velocities, particle arrays, counters, drag flags) lives in `m.store` as plain data: numbers, strings, booleans, arrays and plain objects (use `{ x, y }`, not `p5.Vector` or class instances). Mutate inside it (`m.store.x += m.store.vx`, `m.store.particles.push({ x, y })`), never replace it. Owners' states and data are plain data the host keeps too (return plain values from compute functions). The host saves both at every transition so the user can step back to that moment, edit values and see the module redraw from there.

Only node ids of the module's own nodes are valid. The host owns the canvas and the loop: it creates the 900×600 canvas, clears it every frame (transparent; the light page shows through), calls each module's `draw` inside `push()/pop()` and passes input to every module. Modules must NOT assign anything on `p` (`p.setup`, `p.draw`, `p.mousePressed`, …) and must NOT call `background`, `clear`, `createCanvas`, `resizeCanvas`, `noCanvas`, `noLoop`, `loop`, `redraw`, `frameRate`, `pixelDensity` or `remove`. A full-frame backdrop is a node of its own: fill that node's box. For trails and anything else made from pressed-and-dragged input, derive it from `m.history()` (see below).

Implementation rules:

- Implement each constraint's compute function following its `description` exactly, reading every one of its params with `m.v("nodeId/paramId")` (e.g. a branch length that "is multiplied by the decay ratio at each depth" reads `tree/base-length` and `tree/decay`). Helper functions shared by several compute functions are ordinary local functions of the module; two modules never share them.
- Render each node from its constraints: evaluate its FSM owner(s), which computes the current state's constraints in their order (each building on the properties computed before it), then draw from `owner.data`. Collections' constraints determine their members' group properties (where each goes, how many), objects' constraints the look of their primitive. Param keys stay `nodeId/paramId` whichever constraint holds the param.
- A node usually stands for MANY instances: when its constraints include a count, a distribution/layout rule (e.g. a row, a radial repeat, a scatter) or recursion, generate every instance with that rule inside the node's layout box and apply the per-instance variation its constraints describe, evaluating one owner per instance (`m.fsm(id, key)`) when the instances have state or per-instance properties. A collection with such a constraint repeats its whole subtree (its children are the parts of one instance). Never draw only one copy.
- The module function's own scope holds ONLY function declarations and `const`s that are functions or plain numbers/strings (no `let`/`var`, no arrays, objects or `new` there); a `const` array or object would be hidden state. Locals inside handlers are fine.
- `setup` re-runs only when a value it READ changes; every other value change keeps the store (trails, particles, drag state) and just draws with the new value. So read in `setup` only the values that truly require rebuilding the store (e.g. a particle count that sizes an array) and read everything else in `draw`, so tweaking it never wipes what the user has drawn or played.
- POINTER INPUTS: a constraint's `inputs` say which pointer attribute drives which of its values (`source` → `paramId`, as `how` says). Implement exactly those mappings, in that constraint's compute function: combine the attribute with `m.v` of that property (the property sets how strongly or over what range it acts), take position from the gesture points (`m.history()`) or `p.mouseX`/`p.mouseY` for hover, and speed, direction, distance and duration from consecutive gesture points and their `t`. Nothing else follows the pointer.
- DERIVE FROM THE INPUT, DO NOT BAKE IT. What the user made with input (a trail of shapes along a drag, stamps placed by clicks, strokes, things emitted while dragging) must be computed in `draw`, every frame, from `m.history()` and the CURRENT values: lay the trail out along the recorded path at the current spacing, size and color its items with the current values, keep the current count of the newest. Never store positions, sizes or counts computed from a value at the moment the input arrived. Then changing any value (a slider, a direct manipulation handle) adjusts what is already on the canvas in place, instead of only what is drawn next. Use only the gestures that concern this module (e.g. those that started inside its box). Keep in `m.store` only state that cannot be derived from the input and the values (a running simulation's positions and velocities, a toggled mode), and still read every value in `draw` when using it.
- Deriving from the input runs every frame over ALL of `m.history()`, so the cost of a frame must NOT grow with all the input ever given:
  - Compute what each gesture makes ONCE per gesture with `m.memo`, keyed by its `id`, `rev` and the values it uses. A finished gesture (`done`) does not change, so its result is reused frame after frame; only the gesture being drawn (`done` false) changes while dragging. Changing a value recomputes each gesture once, not every frame.
  - Work that relates items of different gestures (overlaps, hidden lines, collisions, merging) is done incrementally: memoize each gesture's part against the results of the gestures before it, keyed by its own id/rev and the ids/revs of those earlier gestures it reads, with a spatial grid or bounding boxes first so only nearby items are compared, never every item against every item every frame.
  - Keep in `m.store` only state and a light list of what is drawn: one record per drawn item with its position and size (`{ x, y, w, h }`) AND the values that made THIS item look the way it does when they differ between items (the speed it was drawn at, its own count, size, angle, color pick), as plain-named fields on that same record, e.g. `{ x, y, w, h, speed, tips }` — not in a separate structure keyed some other way. Never full outlines, point arrays or caches. Every such record has a stable `id`: the gesture it came from and its place in it (`${g.id}:${i}`), or another id that stays the same while the item exists.
  - Draw a shape as one path rather than hundreds of separate strokes and keep a frame to a few thousand drawing calls. A frame that runs longer than 10 seconds is stopped as a runaway loop.
- Input ends only through input events (`mouseReleased`, `touchEnded`, a described key): never release or cancel a press from `draw` by checking `p.focused`, `p.mouseIsPressed`, `p.touches` or `document.hasFocus()`. The host forwards the pointer as events while the sketch may be unfocused, so such checks cancel drags that are still going on.
- `draw` runs every frame: read the values inside `draw` every frame (do not copy them into `m.store`, so editing a value redraws even a restored moment), and animate with values advanced in `m.store` (or a time an owner's data keeps, advanced by `p.deltaTime`). Do not use `p.millis()` or `p.frameCount` for motion: they cannot be restored.
- Return only the `rulegenModule(...)` calls. Do not include or imitate host blocks or drivers. Do not create a new p5 instance.
- Only p5 drawing, math and local JS. No imports, DOM, storage, network, external assets, eval, Function, timers, exports or markdown fences. Finite loops and bounded recursion; prefer a deterministic seed.
- No technical labels, legends or parameter readouts in the artwork unless the user asks for them.
