## SCENE CODE CONTRACT

Your code is a set of independent MODULES, one per ROOT node (a node whose `parentId` is null; `modules` lists each root id with the node ids it draws). A module is drawn on its own: the user can lift one into another sketch as a reusable brush stamp, copy it several times, and every copy runs the same module code with its own node ids. So the WHOLE program is only this, once per root, in any order:

```js
rulegenModule("<root id>", function (m) {
  // only functions and constants here: algorithm functions, helpers, fixed numbers
  function algo_power_decay(base, ratio, depth) { return base * Math.pow(ratio, depth); }
  const GRAVITY = 0.4;
  return {
    setup() { /* optional: (re)build m.store, e.g. m.store.particles = []; runs again ONLY when a value it read with m.v / m.box changes */ },
    draw() { /* required: draw this root and all of its nodes, every frame */ },
    mousePressed(event) { /* optional input: mouseMoved, mouseDragged, mouseReleased, mouseClicked, doubleClicked, mouseWheel, keyPressed, keyReleased, keyTyped, touchStarted, touchMoved, touchEnded */ },
    stateEntered(nodeId, stateId) { /* optional: a node of this module entered a state */ },
  };
});
```

Nothing may be written outside the `rulegenModule(...)` calls, and modules must not share anything: no top-level variables or functions, no undeclared globals. The factory parameter must be named `m` and is used ONLY as below (call these directly with string-literal arguments, never pass `m` or its functions around):

- `m.v("<key>")` — a live value. For EVERY entry of `parameterBindings` whose node belongs to this module, read it with the EXACT literal key and use it in real geometry, color, timing or behavior so that moving the slider changes the visual. Keys are `nodeId/propertyId` for a scalar property, and `nodeId/propertyId/argId/…` for the scalar arguments of an algorithm call (nested arguments add further segments). Never copy current values as literals and never build keys dynamically.
- `m.box("<node id>")` — `{ x, y, w, h, visible }`: the node's current box in canvas pixels. Place EVERY node of the module inside its box (translate/scale your drawing into it) and skip nodes that are not `visible`, so that moving, copying or hiding a node follows live. Never hardcode positions.
- `m.state("<node id>")` — only for nodes with a machine: `.id` is the current state id and `.elapsed` the milliseconds since it entered it. When the state changes the host swaps the values behind that node's `m.v` keys, so reading `m.v` inside `draw` is enough for most state-dependent appearance. Branch on `.id` when the algorithm or layout itself differs between states; use `.elapsed` for within-state motion.
- `m.emit("<node id>", "<transition id>")` — fire a named event transition of that node (see the interaction contract). Both ids are string literals at every call site; when several transitions share logic, branch to separate literal calls (e.g. `if (inside) m.emit("stars", "enter-star"); else m.emit("stars", "leave-star");`). Timed transitions are applied by the host.
- `m.history()` — the input given so far: an array of gestures (each press → drag → release on the canvas, oldest first, up to 24), each `{ id, rev, points: [{ x, y, t }], done }` in canvas pixels with `t` = ms since its press; `done` is false while it is still held. `id` never changes and is never reused; `rev` changes whenever that gesture changes (a new point, release, or its points being thinned), so a gesture with the same `id` and `rev` has exactly the same points. Read-only: never change it. Hover moves without a press are not in it.
- `m.memo(key, () => value)` — returns the value computed for `key` (a short string or a small array), computing it only the first time. It is the module's cache for what is derived from the input: kept by the host (not in `m.store`, so it is not copied into every inspection step), and entries not used for a few seconds are dropped. Build the key from what the value depends on: gesture `id`s and `rev`s and the values it uses, e.g. `m.memo(["trail", g.id, g.rev, spacing, size], () => layOut(g, spacing, size))`. Never put points, `m.history()` or other large data in a key, and never `JSON.stringify` the history.
- `m.p` (or `p`) — the shared p5 instance to draw with.
- `m.store` — this instance's state object. Everything else that changes between frames or after input (positions, velocities, particle arrays, counters, drag flags) lives in `m.store` as plain data: numbers, strings, booleans, arrays and plain objects (use `{ x, y }`, not `p5.Vector` or class instances). Mutate inside it (`m.store.x += m.store.vx`, `m.store.particles.push({ x, y })`), never replace it. The host saves `m.store` at every state change so the user can step back to that moment, edit values and see the module redraw from there.

Only node ids of the module's own nodes are valid. The host owns the canvas and the loop: it creates the 900×600 canvas, clears it every frame (transparent; the light page shows through), calls each module's `draw` inside `push()/pop()` and passes input to every module. Modules must NOT assign anything on `p` (`p.setup`, `p.draw`, `p.mousePressed`, …) and must NOT call `background`, `clear`, `createCanvas`, `resizeCanvas`, `noCanvas`, `noLoop`, `loop`, `redraw`, `frameRate`, `pixelDensity` or `remove`. A full-frame backdrop is a node of its own: fill that node's box. For trails and anything else made from pressed-and-dragged input, derive it from `m.history()` (see below).

Implementation rules:

- Implement every library algorithm a module uses INSIDE that module as a local function named after its id (e.g. `function algo_sine_wave(args, t) {…}`) following its Korean description exactly, and call it wherever the module's nodes use it. Two modules using the same algorithm each define their own copy. An argument that is itself an algorithm call means "evaluate that algorithm to obtain this parameter" (e.g. a length driven by power-decay over depth).
- Render each node from its stack of `transformations`, applied in order (each builds on the previous result): collections apply them to all of their members (children), objects draw their primitive. Property keys stay `nodeId/propertyId…` whichever transformation holds the property.
- A node usually stands for MANY instances: when its properties include a count, a distribution/layout algorithm (e.g. `repeat-layout`, `radial-repeat`, `scatter`) or recursion, generate every instance with that algorithm inside the node's layout box and apply the per-instance variation its algorithms describe. A collection with such a property repeats its whole subtree (its children are the parts of one instance). Never draw only one copy.
- The module function's own scope holds ONLY function declarations and `const`s that are functions or plain numbers/strings (no `let`/`var`, no arrays, objects or `new` there); a `const` array or object would be hidden state. Locals inside handlers are fine.
- `setup` re-runs only when a value it READ changes; every other value change keeps the store (trails, particles, drag state) and just draws with the new value. So read in `setup` only the values that truly require rebuilding the store (e.g. a particle count that sizes an array) and read everything else in `draw`, so tweaking it never wipes what the user has drawn or played.
- DERIVE FROM THE INPUT, DO NOT BAKE IT. What the user made with input (a trail of shapes along a drag, stamps placed by clicks, strokes, things emitted while dragging) must be computed in `draw`, every frame, from `m.history()` and the CURRENT values: lay the trail out along the recorded path at the current spacing, size and color its items with the current values, keep the current count of the newest. Never store positions, sizes or counts computed from a value at the moment the input arrived. Then changing any value (a slider, a direct manipulation handle) adjusts what is already on the canvas in place, instead of only what is drawn next. Use only the gestures that concern this module (e.g. those that started inside its box). Keep in `m.store` only state that cannot be derived from the input and the values (a running simulation's positions and velocities, a toggled mode), and still read every value in `draw` when using it.
- Deriving from the input runs every frame over ALL of `m.history()`, so the cost of a frame must NOT grow with all the input ever given:
  - Compute what each gesture makes ONCE per gesture with `m.memo`, keyed by its `id`, `rev` and the values it uses. A finished gesture (`done`) does not change, so its result is reused frame after frame; only the gesture being drawn (`done` false) changes while dragging. Changing a value recomputes each gesture once, not every frame.
  - Work that relates items of different gestures (overlaps, hidden lines, collisions, merging) is done incrementally: memoize each gesture's part against the results of the gestures before it, keyed by its own id/rev and the ids/revs of those earlier gestures it reads, with a spatial grid or bounding boxes first so only nearby items are compared, never every item against every item every frame.
  - Keep in `m.store` only state and a light list of what is drawn for inspection: one record per drawn item with its position and size (`{ x, y, w, h }`) AND the values that made THIS item look the way it does when they differ between items (the speed it was drawn at, its own count, size, angle, color pick), as plain-named fields on that same record, e.g. `{ x, y, w, h, speed, tips }` — not in a separate structure keyed some other way. Never full outlines, point arrays or caches.
  - Draw a shape as one path rather than hundreds of separate strokes and keep a frame to a few thousand drawing calls. A frame that runs longer than 10 seconds is stopped as a runaway loop.
- `draw` runs every frame: read the values inside `draw` every frame (do not copy them into `m.store`, so editing a value redraws even a restored moment), and animate with `m.state(…).elapsed` or values advanced in `m.store`. Do not use `p.millis()` or `p.frameCount` for motion: they cannot be restored.
- Return only the `rulegenModule(...)` calls. Do not include or imitate host blocks or drivers. Do not create a new p5 instance.
- Only p5 drawing, math and local JS. No imports, DOM, storage, network, external assets, eval, Function, timers, exports or markdown fences. Finite loops and bounded recursion; prefer a deterministic seed.
- No technical labels, legends or parameter readouts in the artwork unless the user asks for them.
