## SCENE CODE CONTRACT

The host defines, before your code:

- `rulegenParams` — a constant object of live values. For EVERY entry of `parameterBindings`, read its value with the EXACT literal expression `rulegenParams["<key>"]` and use it in real geometry, color, timing or behavior so that moving the slider changes the visual. Keys are `nodeId/propertyId` for a scalar property, and `nodeId/propertyId/argId/…` for the scalar arguments of an algorithm call (nested arguments add further segments). Layout keys `nodeId/@x`, `nodeId/@y`, `nodeId/@w`, `nodeId/@h` give each node's current bounding box in canvas pixels, and `nodeId/@visible` (boolean) whether it is shown: place EVERY node with its layout keys (translate/scale its drawing into that box) and skip hidden ones, so that moving, dropping or hiding a collection/object in the layer editor changes the result live. Layout keys are not required by the validator, but a node drawn at a hardcoded position will not follow the user's direct manipulation. Never copy current values as literals, never use computed/dynamic keys, never pass `rulegenParams` around as a whole, never declare or write it.
- `rulegenState["<node id>"]` — only for nodes that have a machine: `.id` is that node's current state id and `.elapsed` the milliseconds since it entered the state. When a node's state changes the host automatically swaps the values behind that node's `rulegenParams` keys, so reading `rulegenParams[...]` inside `p.draw` is enough for most state-dependent appearance. Branch on `rulegenState["<node id>"].id` when the algorithm or layout itself differs between states, and use `.elapsed` for within-state motion. Never write to it.
- `rulegenEmit("<node id>", "<transition id>")` — fire a named event transition of that node (see the interaction contract). Timed transitions are applied by the host.
- You may assign `p.stateEntered = (nodeId, stateId) => { … }` to reset local simulation data when a node enters a state.

Implementation rules:

- Implement every library algorithm used by the scene ONCE as a reusable local function named after its id (e.g. `function algo_sine_wave(args, t) {…}`) following its Korean description exactly, and call it wherever the scene uses it. An argument that is itself an algorithm call means "evaluate that algorithm to obtain this parameter" (e.g. a length driven by power-decay over depth).
- Render each node from its stack of `transformations`, applied in order (each builds on the previous result): collections apply them to all of their members (children), objects draw their primitive. Property keys stay `nodeId/propertyId…` whichever transformation holds the property.
- A node usually stands for MANY instances: when its properties include a count, a distribution/layout algorithm (e.g. `repeat-layout`, `radial-repeat`, `scatter`) or recursion, generate every instance with that algorithm inside the node's layout box and apply the per-instance variation its algorithms describe. A collection with such a property repeats its whole subtree (its children are the parts of one instance). Never draw only one copy.
- If any node has a machine: draw the complete current scene in `p.draw` every frame, read the values inside `p.draw`, and do NOT call `p.noLoop()`. Otherwise you may draw once in `p.setup` and call `p.noLoop()`.
- Return only your drawing program: assign `p.setup` (which MUST call `p.createCanvas(900,600)`) and optionally `p.draw`, input callbacks and `p.stateEntered`, using the variable `p` provided by the host. Do not include or imitate host blocks or drivers. Do not create a new p5 instance.
- Only p5 drawing, math and local JS. No imports, DOM, storage, network, external assets, eval, Function, timers, exports or markdown fences. Finite loops and bounded recursion; prefer a deterministic seed.
- No technical labels, legends or parameter readouts in the artwork unless the user asks for them.
