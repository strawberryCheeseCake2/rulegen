## PER-NODE STATE MACHINE (declarative FSM)

A state machine belongs to **one node** (a collection or an object), not to the whole frame. Every collection and every object can have its own FSM and current state; repeated items of one node each have their own state while sharing the node's FSM definition. Behavior for an individual member goes in its object's FSM, behavior shared by the group in its collection's FSM.

- `machine = { initialState, states[], transitions[] }`.
- Each state: `{ id, label, description, constraintIds[] }`. `constraintIds` lists, IN EVALUATION ORDER (dependencies first), the constraints of THIS node that apply in that phase: whenever the code evaluates the node's FSM in that state, each listed constraint computes its property and stores it before the next one runs. A phase in which a property depends on something else gets its OWN constraint for that property (same `property`, its own id and description, e.g. `size` → `size-pressed`), listed in that state instead of the other one. New constraints a machine needs are given in `constraints` beside it (new ids only; existing constraints are referred to by id and never redefined).
- The description explains the relationships that hold in that phase (what each listed constraint does there), the eligible user inputs and the exit/completion condition.
- Transitions: `{ id, from, to, event, label }`. The code takes a transition by dispatching its `event` while the owner is in `from`: a real user input (pointer enters, press, drag start, release, key), a code-detected condition (contact, reaching a target, an absorption, a count reached, a timer the code keeps finishing). One state has at most one transition per event; different states may share an event.

FINE-GRAINED STATE PLANNING: Identify the distinct object roles, group behavior, interaction phases and lifecycle changes, and give a phase its own state when different relationships apply (a different set or order of constraints), different actions become possible, or the node changes how it participates in the artwork. Decompose as finely as the actual behavior supports, up to 32 states and 128 transitions; a rich interaction normally uses 8–20 meaningful states. Separate every change in user intent, input availability, movement direction, speed regime, contact, selection, appearance, growth, completion, cancellation, recovery and return. A drag example can distinguish available, hover feedback, pressed/armed, drag beginning, dragging, valid drop preview, released, snapping/settling, committed and returning; a motion example can distinguish anticipation, acceleration, cruising, approach, contact, response, deceleration, settling and recovery. These are examples, not a template. Do not add duplicate states whose constraints are the same and whose behavior does not change. A node with one mode of behavior throughout has no machine (`null`).

SEMANTIC TRANSITION LABELS: Every `label` concisely describes WHY the node changes, naming the user action, target or completion condition, e.g. `"Pointer enters circle"`, `"Drag starts"`, `"Drop on valid area"`, `"Growth complete"`, `"Absorbed by a larger heart"`. Never use bare IDs, `A→B`, `Next`, `Transition 1` or only a duration. `event` is a short kebab-case name for the same thing (`"pointer-enter"`, `"drag-start"`, `"drop"`, `"grown"`, `"absorbed"`). Use stable descriptive ids. Include relevant cancellation, re-entry and return paths. Write labels and descriptions in English. Never render this planning text in the artwork.
