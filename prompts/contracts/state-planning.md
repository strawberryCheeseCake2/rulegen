## PER-NODE STATE MACHINE

A state machine belongs to **one node** (a collection or an object), not to the whole frame. It changes that node's own property values over time or in response to user input. Other nodes keep their own machines.

- `machine = { initialState, states[], transitions[] }`.
- Each state: `{ id, label, description, values[] }`. `values` lists `{ propertyId, value }` for properties of THIS node whose value differs in that state. Omitted properties keep the node's base value. A state value MUST keep the same structure as the base property value: a number stays a number with the same range shape, an algorithm call stays a call of the same algorithm with the same argument ids — only scalar values change between states. If a phase needs a new controllable quantity, add it as a property of the node first (in `transformation`).
- The description explains the entry appearance, the behavior while active, the eligible user inputs and the exit/completion condition.
- Transitions: `{ id, from, to, label, trigger, afterMs }`. `trigger: "after"` for genuinely timed phases (afterMs = integer milliseconds 100..60000, long enough to see the motion); `trigger: "event"` for real user input or a code-detected completion (afterMs = 1000, ignored). Waiting/hover/pressed states must not advance just because time passed.

FINE-GRAINED STATE PLANNING: Decompose the node's behavior as finely as its actual behavior supports, up to 32 states and 128 transitions. Do not summarize a multi-step dynamic or interactive behavior as only Idle/Active/Done. For a rich interaction normally use 8–20 meaningful states. Separate every change in user intent, input availability, movement direction, speed regime, contact, selection, appearance, growth, completion, cancellation, recovery and return. A drag example can distinguish available, hover feedback, pressed/armed, drag beginning, dragging, valid drop preview, released, snapping/settling, committed and returning; a motion example can distinguish anticipation, acceleration, cruising, approach, contact, response, deceleration, settling and recovery. These are examples, not a template. Do not add duplicate sampled frames of unchanged behavior. A truly static node has no machine.

SEMANTIC TRANSITION LABELS: Every `label` concisely describes WHY the node changes, naming the user action, target or completion condition, e.g. `"원 위에 포인터 진입"`, `"드래그 시작"`, `"유효한 영역에 놓기"`, `"성장 완료"`, `"정착 후 대기"`. Never use bare IDs, `A→B`, `Next`, `Transition 1` or only a duration. Use stable descriptive ids. Include relevant cancellation, re-entry and return paths. Prefer Korean labels and descriptions. Never render this planning text in the artwork.
