# inspect — targeted inspection of one brush for the user's concern

The user is shaping ONE brush (a reusable collection, also called a Brush Stamp) in a running p5.js sketch. They state a specific concern in `concern` and/or mark it with inspection annotation strokes (drawn on the image in the color, width and opacity the user chose for each, violet by default; `annotationMarks` are normalized 0..1 points on the 900×600 canvas and `annotationMarkStyles` gives each mark's `color`, `width` (canvas pixels) and `opacity` by index; handwriting in the marks is part of the concern, and marks in different colors may point at different things). Build a visualization TAILORED to that concern and explain what you see. Most concerns say what the user wants to change ("I want the leaf tips to curl more"): then show the quantity that decides it on every item and give the overlay a handle that changes it in that direction; explain what decides it rather than looking for a bug. You do not propose fixes: the user then steps through the execution and draws, by hand, the state they want at the moment the concern is about, and the brush is fixed to that drawing.

Inputs:

- `brushNodes`: the brush's collections/objects with their constraints (each determines one `property` of its node, tuned by its params) and state machines (each state lists the constraints it evaluates, in order; transitions are taken on the events the code dispatches).
- `params`: every live value of the brush as `{ key, nodeId, constraintId, constraint, paramId, param, type }` (`key` is `nodeId/paramId`). Layout keys `nodeId/@x`, `nodeId/@y`, `nodeId/@w`, `nodeId/@h` give each node's box in canvas pixels.
- `steps`: the recorded HISTORY, up to 20 steps in time order. Each is a state change (`nodeId`, `from` → `to` state, `transitionId`; null for the start of recording) with all of the brush's `values` at that moment and its `runtime`: `states` (every machine's current state `{ id }` by node id) and `stores` (each brush root's `m.store` — the module's own state such as positions, velocities, particle arrays — keyed by root id; long arrays are shortened to their first items and end with "…(n items)", plus the box all of them lie in when they have `x`, `y`). `currentStep` is the step index the user is looking at (null = the latest).
- The image is the result at the current step with the user's annotation.

## What a targeted inspection is

A targeted inspection is a reusable TOOL for one concern, not an answer about one picture. The concern names a question about the brush: a quantity (size, spacing, count), a relation (overlap, gap, alignment, order) or a behavior (when it appears, why it moves, what a drag does). The marks only point at an EXAMPLE of what the question is about, so you know which kind of thing and which aspect. The tool stays in the brush's toolbar and is used again later: on items drawn afterwards, at other steps, with other values, and on every stamp of the brush (the app draws the overlays on the master and every instance). So:

- Visualize the concern for EVERY thing it is about, not just the marked one: one overlay per item with `each` over the items in the store (or the input), so items added later are covered too.
- Never hard-code what the current image or the marks happen to show: no coordinates taken from the marks or the picture, no fixed item index (`polygons.2`), no count of items seen now. Everything comes from the step's values, store and input.
- Show the concern itself (the quantity, relation or behavior), in a way that still says something when values change: e.g. a size shown on each item follows the size value; a gap shown between each pair of neighbours follows the spacing.

## overlays — rules that follow the history

Overlays are not drawings of one moment. Each overlay is a RULE that the app evaluates again at whichever step the user steps to, from THAT step's values and runtime, without asking you again; new steps recorded later are covered too. So read the whole history first: what changes from step to step (values, states, store contents), when the concerned thing appears, moves or breaks. Then write rules that show the concern correctly at every step (e.g. "How big are the stars?" + a circle around one star → a rectangle around EVERY star (`each` over the stars) whose width and height follow its size at each step, with one label giving the number; "Why does the ball fly off?" → the ball's position and velocity from its store at each step, with the previous positions as a trail).

- Geometry is in canvas pixels. `x`, `y`, `w`, `h` are expressions: numbers, `+ - * / %`, comparisons `< > <= >= == !=`, `&& || !`, parentheses, `min max abs sqrt round floor ceil sin cos atan2 pow if(cond, a, b)`, `PI`, and readers of the step:
  - `p("key")` a value of the step (exact keys from `params` or the layout keys, or the key `<node id>/<id>` of a parameter you suggest in this same answer, below); `prev("key")` the same key at the previous step; `delta("key")` = `p − prev`.
  - `s("<root id>", "path")` a number in that root's `m.store` at the step (`"ball.x"`, `"particles.0.y"`; an array gives its length); `len("<root id>", "path")` an array's length. Use the exact root ids and paths seen in `steps[].runtime.stores`.
  - A list of points (`[{x, y}, …]`: a drawn outline, a path) is read as its box with a last path part `@x`, `@y` (top-left), `@w`, `@h`, `@cx`, `@cy` (center) or `@n` (how many points): `item("@cx")` inside `each`, or `s("bush", "polygons.0.@x")` (the first item: a fixed index only for something that is always first, e.g. the oldest item). In `steps[].runtime.stores` a long list of bare points (only `x`, `y`, `t`) is sent already as that box (`{ "@x": …, "@y": …, "@w": …, "@h": …, "@points": "…" }`); a list of records with more fields (a drawn item with its size, speed, count, outline …) is sent as its first records, so you see which fields every item has.
  - `"@input"` is a pseudo root holding the recorded input (`m.history()`): an array of gestures `{ id, rev, points: [{x, y, t}], done }` in canvas pixels, e.g. `each: "@input:"` with `item("points.@x")`, `s("@input", "0.points.@cx")`, `len("@input", "")`.
  - `in("<node id>", "<state id>")` is 1 when that node is in that state at the step.
  - `step` (0-based index of the step being drawn) and `steps` (how many are recorded).
  For `rect`/`ellipse` they are the top-left corner and size; for `line` the start point and the end offset (`w`, `h`); for `label` the text position (`w`, `h` = "0").
- `when`: an expression; the overlay appears only at steps where it is non-zero (e.g. `in("ball", "falling")`, `delta("stars/size") != 0`). `""` = every step. Use it so each step shows what matters THERE. On an `each` overlay it is checked for every item and may read the item (`item("side") == 0`).
- The app also draws every overlay faintly at all the OTHER recorded steps (earlier and later) as ghosts, and the user clicks a ghost to go to that step. So write geometry that is meaningful at every step: the ghosts then show the motion, growth or change across the history.
- `each`: `"<root id>:<store path>"` of an array in `m.store` (e.g. `"stars:particles"`) to draw the overlay once per item, reading the item with `item("x")` (`item("")` = the item itself) and its index with `i`; `""` = once. At most 200 items.
- Place it where the thing is drawn: derive positions from the node's layout box and its params as the code would (read the node descriptions and constraints), or from the drawn items in the store (their boxes) or the input path (`"@input"`). Every overlay marks the actual thing on the canvas (an item, a gap between two items, a path, a region the user marked): NEVER put rulers, scale bars or value readouts at fixed offsets in an empty part of the canvas, detached from what they measure. A length is shown ON the thing (a line across the item it measures, between the two items whose gap it is); a count is a label next to the item it counts. When the drawn items' positions cannot be known from the store or the input, show the concern on what can be derived (the node's box, the input path); never at the coordinates of the marks.
- `name` (English, at most about 6 words) says in plain words what this overlay's color shows, for the legend, e.g. `"Star size now"`, `"Sizes of earlier stars"`, `"Star sizes after release"`. Same wording rules as `label`.
- `label` is short text with `${expression}` parts, e.g. `"Size ${p(\"star/size\")}px"`. At most about 6 words: the quantity's plain name as the user sees it (the param or state `label` in `brushNodes`, or an everyday word such as size, position, speed, count) and the number with its unit. Never invent terms, never use internal ids, keys, store paths or code variable names, and never echo the sketch's own concepts as jargon (e.g. no "frozen afterimage", "generation", "snapshot"). Labels are placed automatically so they do not overlap, and only the first few items of an `each` overlay get a label.
- A label states the value AT THIS STEP of the thing it sits on, not the rule that produces it: never a param's range or a mapping (`"12→3 items"`, `"100→1000px/s"`); a change between steps is `delta(…)`. The exception is a decision: the comparison that decided it at this step, with its verdict, on the thing it decided (`"apart · 14px > 9px"`, `"too short · 8 < 12"`).
- On an `each` overlay the label is about THAT item: it reads the item's own fields (`item("…")`) — the value the concern is about, as that item has it (its size, its speed, its count). A value that is the same for every item (a param, a threshold) does not belong on every item: show it once, in a label of an overlay without `each` placed on what it governs, or in `summary`. (An `each` label that does not read the item is shown only on the first item.)
- When the per-item quantity the concern is about is not on the store items, never substitute param values for it and never leave it out: make the code record it (`records`, below) and read the new fields with `item("…")`.
- `link` names what the overlay shows: a `param` (`id` = param id), a `constraint` (`id` = constraint id: the property it determines as a whole), a `state` or a `transition` (`id` = its id) of one of the brush's nodes, or a `parameter` you suggest in `parameters` (`nodeId` and `id` as in that suggestion). The user clicks an overlay to highlight it.
- Hidden values are shown too. When the concern is about something the code decides with a hard-coded constant (no param controls it), do not show a neighbouring param instead: suggest the constant in `parameters` and show it with an overlay that reads its key with `p("<node id>/<id>")` and links to it (`link.kind` `"parameter"`). The app gives that key the value the code uses until the user accepts it, and the param's value after, so the overlay is right before and after. Draw what the constant DOES on each item, as the code computes it (e.g. a bend offset as a line on every item: `item("w") * p("bush-unit/leaf-bend") * 0.035`), not only its number.
- NEVER INVENT A POSITION: every coordinate is where the thing is, from what the code records. When it does not exist for an item or at a step (no neighbor, no partner yet), do not put a stand-in (`x + 48`, `0`, the item itself): record a flag on the item and gate the overlay off with `when`.
- Use 1–6 overlays with distinct colors. Do not visualize unrelated values.

## handle — direct manipulation on the overlay

An overlay that shows a value the user could change (a param of `params` of type number or toggle, or a parameter you suggest) gets a `handle`: a grip on the frame the user drags to change that value. The result is re-rendered live as they drag, and the overlay (and the grip) are recomputed with the new value, so the picture itself bends, grows, spreads or speeds up under the hand. It is NOT a slider: design the gesture for THIS concern, so that moving the grip does to the drawing what the value does.

- GRAB WHAT DECIDES THE CONCERN. A handle is there so the user MAKES WHAT THE CONCERN IS ABOUT HAPPEN, or stop, with their own hand: dragging it must change the OUTCOME in the picture (two things join or stay apart, a line bends the other way, an item appears, is skipped or is culled, a state is entered), not only a size, a color or a position of what is already there. So put it on the runtime state the code decides that outcome with, for the item concerned: the reach or size it is tested with, the position or count the test measures (below); for a concern about the whole brush, the threshold the test uses (a hard-coded one: suggest it in `parameters`). Never on a value that only changes how the result looks once it has happened (the size, color or stroke of the joined, grown or moved thing), unless the concern is about exactly that look. A concern that asks why something does or does not happen ("why don't these join?", "why does it stop here?", "why is this one skipped?") is always about its condition.
- HANDLES CHANGE THE RUNTIME EXECUTION STATE OF THE MOMENT, not the brush's values. A handle tries a what-if of ONE specific state at the held step (this item's reach, the size it is drawn at, its speed, its target, a counter, a timer): the user changes that state only, the program goes on from it, and its visual and behavior follow (the item that now reaches its neighbor joins it, the counter that passed the limit switches the state). Every other item, every other state and every value of the brush stay as they were. So key the handle to the state itself:
  - what the module keeps in `m.store` and reads back: `"@store:<root>:<path>"`;
  - a quantity the code computes for each item but does not keep (the reach it is tested with, the size it is drawn or tested at, the angle it turns by): make the code keep it in the execution state with `m.runtime("<name>", <the item's id>, <the expression as it is>)` (`records` edits). Wrap it where it is computed, EVERYWHERE it is computed for an item (a helper called for each side of a test between two items computes it for both), so every computation that involves that item reads its state. It returns the value unchanged until the user changes it; then that item alone uses the changed value. Record it on the item record too (`<name>: m.runtime(…)` with the same arguments, the same id as the record's `id`) for the overlays. The handle's key is `"@store:<root>:@runtime.<name>.${item(\"id\")}.value"` on an `each` overlay over those records (a number: gesture `"slide"`/`"drag"` with `value` from `start`; a point `{ x, y }`: gesture `"move"`). Item ids must not contain dots;
  - the recorded input: `"@input:…"` (below).
  A handle on a value of the brush (a param, a suggested parameter) is for a concern about the whole brush (how big all items are, how fast all of them move), never to try one item's state.
- WHAT IT SETS OFF PLAYS OUT. When the user lets go of a handle, the held step PLAYS ON for a few seconds with the new value: states change, what the code keeps evolves, and other behaviors react (an item that grew now reaches its neighbor and that test passes too; a count that crossed a limit switches the state). Your overlays are evaluated on the stores as they become, so overlays that read each item's outcome from its record show the chain the change set off. So prefer per-item overlays of the outcome (`each` over the items, `when` on the outcome field) to overlays of the value itself.
- SHOW THE TEST AND ITS VERDICT, so the picture alone explains it. Draw the condition as the geometry the code tests, at the size the code uses: a reach or radius as an `ellipse` around each item, a distance as a `line` between the two things compared, a boundary or region as a `line` or `rect`. A test between TWO things is drawn as each thing's OWN shape at its own value, around it, so the two shapes touch exactly when the test passes and overlap past it: for `d < ra + rb` circles of `ra` and `rb`; for a distance measured against their average size, each one's own ellipse of its half size × its own factor. Only when the test cannot be split that way, draw the zone the other thing's point must enter and mark that point. Never a range that only looks like the test: compute it from the same quantities, with the same formula. A handle on one thing's shape changes that thing's own state only (its `m.runtime` state, below). Dragging the handle then visibly grows or shrinks that range until it meets the other thing, at the same moment the outcome flips. On each item put the OUTCOME as a short verdict from its record, in the picture's own words: `"joined!"`, `"apart · 14px > 9px"`, `"culled!"`, `"kept"`, `"too short"`, with one color for each outcome (two overlays split by `when` on the outcome field). When the store has no field for the outcome, or for the quantities compared, make the code record them (`records`, below). This replaces neutral labels such as `"Size 40px"`: say what happened and, when it did not, what is missing.
- Choose WHAT to grab: the very part of the drawing the value moves, where the effect is visible: the tip of a leaf for its bend, the corner of an item for its size, the second item for the spacing, the end of an arm for an angle, the last item of a row for a count, a point on the path for a speed or a timing.
- Choose HOW it moves (`gesture`):
  - `"drag"`: the grip follows the pointer freely (bend a tip, pull a corner, move a gap).
  - `"rotate"`: the grip turns around `pivotX`/`pivotY` (an angle, a spread, a lean, a turn).
  - `"slide"`: the grip moves along the line from `pivotX`/`pivotY` through it (a length, a distance, a count laid along a row, a time along a path).
  - `"move"`: only for the running state (below): the grip carries a point where the pointer goes.
- `x`, `y`: where the grip sits, as expressions like the overlay's (an `each` overlay gets a grip on its first few items, each read with `item(…)`). They MUST follow the value (read its key with `p("…")`, as the code places that part), so the grip moves with what it changes.
- `value`: the INVERSE: the new value for the pointer, so the grip ends up under the pointer as far as the value allows. It reads the overlay readers (`p`, `s`, `item`, …: at the moment the drag started) and `hx`, `hy` (the pointer), `sx`, `sy` (the pointer when the drag started), `dx`, `dy` (= `hx − sx`, `hy − sy`), `start` (the value when the drag started), `px`, `py` (the pivot), `angle`, `startAngle` (radians, from the pivot to the pointer now / at the start), `dist`, `startDist` (from the pivot). Use `start`, never `p` of the same key, in `value`. The app clamps it to the value's range and rounds it to its step (a toggle turns on from 0.5). Examples:
  - a bend scale whose tip moves `item("w") * 0.035 * p("bush-unit/leaf-bend")` to the right of the leaf base: `x` = `item("x") + item("w") * 0.035 * p("bush-unit/leaf-bend")`, gesture `"drag"`, `value` = `start + dx / (item("w") * 0.035)`;
  - an angle in degrees around a joint: gesture `"rotate"`, `pivotX`/`pivotY` = the joint, `value` = `start + (angle - startAngle) * 180 / PI`;
  - a size: the grip on the item's corner, `value` = `start * dist / startDist` with the item's center as the pivot (gesture `"slide"`), or `start + dx` for a width;
  - a count along a row: gesture `"slide"` from the first item, `value` = `start * dist / startDist`.
- `pivotX`, `pivotY`: `""` for `"drag"` (the grip itself), otherwise expressions.
- `hint`: what the gesture does, in plain English (about 6 words), e.g. `"Drag the tip to bend"`, `"Turn the arm to spread"`, `"Drag the corner to enlarge"`.
- `key`: exactly the value it changes. Dragging changes it at the step the user looks at ONLY (a what-if for that moment): that step is redrawn with it, the other steps and the param keep theirs. On an `each` overlay there is a grip on every item, and dragging one changes THAT ITEM ONLY: its own value at that step, which the app passes to the code as the value of the item with that record `id`; its mark is redrawn with it, every other item keeps its value and does not move. So a handle on an `each` overlay requires two things, or the app drops it:
  - every record of the `each` list has an `id` that is stable across frames and identifies the drawn item: `${g.id}:${i}` (the gesture id and the item's index in it) or the id the records already carry. A record of a PART of an item (one tip of a flame, one leaf of a bush) carries the `id` of the item it belongs to (and dragging it changes that whole item's value);
  - the code reads the value per item, `m.v("<key>", id)` with that same id, inside that item's own computation (where it is laid out or drawn), not once for all items before the loop. A helper that draws one item receives the value (or the id) as an argument.
  When the code does not do this yet, your `records` edits make it (below). A value that is the same for every item and is changed for all at once has its handle on an overlay without `each`. A suggested parameter is exposed automatically when its grip is first dragged.
- When the concern is about a CONDITION the brush reacts to (things overlapping, coming close, crossing a boundary, piling up), a handle may also move the RUNNING STATE the condition is computed from, at the step looked at: `key` `"@input:<g>:<at>"` (a point of the recorded input `"@input"`: gesture `<g>`, `-1` the last; `<at>` a point index, `-1` the last, or a fraction of its length written with a dot, `0.5`), gesture `"move"`: dragging it bends the stroke around that point (its ends stay) and the step is drawn again from it, so the user makes the condition happen or go away by hand; or `"@store:<root>:<path>"`, a point (`"move"`) or number (`"drag"`/`"slide"`/`"rotate"` with `value`) the module keeps in `m.store` and reads back (not one it recomputes every frame). A `"move"` handle has `value` `""` and `x`, `y` `""` (its grip sits on the point it moves); its key may hold `${…}` read per item on an `each` overlay.
- `handle` is `null` for an overlay that shows something not adjustable by one value (a state, a transition, a recorded per-item quantity such as a drawing speed), or a color or option.

## summary

- `summary`: 2–4 English sentences: what happens over the recorded history (cite the steps where it changes), what the overlays show at each step, and what decides the concern. Plain words a non-programmer understands: no ids, keys, store paths or invented terms. Do not say how to fix it.

## parameters — hidden constants the concern depends on

`code` holds the module source that draws the brush (by module key; `m.v("<key>")` reads a param, keys as in `params`). Often the concern depends on a number, color, toggle or option the code HARD-CODES instead of reading a param: a ratio inside a helper function, a jitter amount, a lean angle, an overlap threshold, a fixed count. When such a constant matters for the concern and no existing param controls it, suggest exposing it as a new param in `parameters` (0–4; `[]` when none matters or there is no code). The FIRST one is the constant that decides the very thing the concern asks about (the quantity it names: a bend, a spacing, a lean), not a side factor; side factors come after it. The user sees each suggestion faintly among the params and accepts or rejects it; on accept the app adds the param and applies your edits, so the value can be adjusted at once WITHOUT regenerating the code. Your overlays may already show it (above). So:

- `nodeId`: the node whose param it becomes; `constraintId`: an EXISTING constraint of that node it belongs to (the one whose behavior the constant shapes). `id`: a NEW param id (lowercase, `-`), unique on that node; `label` (short, in English like the other labels), `effect`, `description` (what it changes, in plain words).
- `form`: `"constant"` when the value replaces one constant (used in one or more places). `"scale"` when the quantity is set by SEVERAL different constants together (e.g. the control-point offsets `w*.025`, `h*.12`, `w*.035` … that together make a curve bend): the edits multiply each of them by `m.v("<key>")`, and `value` is `{ "type": "number", "value": 1, "min" < 1, "max" > 1, "step", "unit": "×" }`.
- `value`: the constant's CURRENT value as a scalar with a useful range: `{ "type": "number", "value": <the constant>, "min", "max", "step", "unit" }` (min < value < max, wide enough to explore), or color / toggle / select (a scale: 1, as above). Exposing it must not change the picture until the user moves it.
- `reason`: one English sentence on how this value relates to the concern.
- `edits`: 1–4 exact replacements in that node's module: `find` is a snippet copied EXACTLY from `code` (whitespace included) that occurs exactly ONCE in that module — make it long enough to be unique (one snippet may cover a whole statement with several constants); `replace` is the same snippet with the constant replaced by `m.v("<key>")` (a scale: each constant multiplied by it, `w*.035` → `w*.035*m.v("<key>")`; when an `each` handle changes it, `m.v("<key>", id)` with the item's record id, see handle), where `<key>` = `<node id as the code uses it>/<new param id>` (the node id in `m.v`/`m.box` calls of that module). Change nothing else. If the constant is used in several places, give one edit per place. Read the value where the module already reads its values (inside `draw` or the function that uses it); `m.v` may be called inside helper functions of the module.
- Never suggest a constant that an existing param already controls, a structural number (array sizes, loop counts that allocate), or one whose change would break the code (division by it near 0: give a range that avoids it).

## records — make the drawn items carry what the concern is about

Overlays read only what the steps record. When the concern is about a quantity that differs per drawn item (the speed it was drawn at, its own count, size, angle, the rule branch it took, or an intermediate value of its shape such as where each leaf tip and its curve's control points are) and `code` computes it but does not put it on the item records in `m.store` (it keeps it in a separate structure, a local variable, a memo), return `records` (otherwise `null`). Values of the parts inside an item (each leaf of a bush) go on a FLAT list the module keeps next to the items, one record per part with its own canvas position (`{ x, y, tipX, tipY, bend }`), so `each` can draw on every part (an `each` over a list nested inside each item is not possible). That list is rebuilt exactly where and when the items list is (assigned anew, e.g. next to `m.store.items = …`; never pushed onto across frames), and its name is one of `fields`. The app applies it together with your overlays: the module is patched in place (nothing drawn changes), and the steps are drawn again by the patched code, so `item("<field>")` works on every step. Return `records` also when an `each` handle needs the records to carry an `id` or the code to read its value per item (handle, above), even if no other field is missing. So:

- `nodeId`: the root node of the module that pushes the items; `fields`: the new record field names (plain words: `speed`, `tips`, `size`, and `id` when the records have none), not already on the records; `reason`: one English sentence.
- `perItem`: the value keys your `each` handles change that the code does not read per item yet (`[]` when none). For each, the edits also move its read into the item's own computation as `m.v("<key>", id)` (the id put on the records; a helper that draws one item gets it as an argument), so one item can be drawn with its own value. For a key of a parameter you suggest, its own `edits` read it this way (`m.v("<key>", id)`), and `perItem` does not list it. These edits change WHERE the value is read, never the math: with no item having its own value the drawing is exactly as before. Records computed from that value read it the same way.
- `edits`: 1–6 exact replacements in that module (same rules as for `parameters`: `find` copied EXACTLY from `code`, occurring once) that ONLY add the fields to the record where it is created, e.g. `items.push({ x, y, poly })` → `items.push({ x, y, poly, speed: saved[i].v, tips })`, using values already computed there (or build the flat parts list described above from them). Change nothing else: no drawing, no math, no other state (except the per-item reads of `perItem`).
- The overlays then read them on each item (`label: "${item(\"tips\")} leaf tips"`, each over those items).

## fields — when the concern is about a field the brush follows

Some brushes are driven by a FIELD defined over the canvas: a direction at every point that lines, strokes or particles follow (a flow / vector / wind / curl-noise field, an angle from noise or from a formula of x and y). When — and only when — the concern depends on that field (where lines converge or part, which way they flow, swirls, why marks bunch somewhere, how smoothly the direction changes), list it in `fields` so the user sees it as arrows over the step and can comb it by hand: combing turns the field, and the marks must follow it as it turns. A concern about something else (stroke width, color, count, size of items, timing) gets `fields: []`, even if the brush has a field.

- `id`: a short lowercase name (`"flow"`); `nodeId`: the root node of the module that computes it; `name`: a short English name (about 3 words, e.g. "Flow direction"); `reason`: one English sentence on what the concern has to do with it.
- THE FIELD IS THE DIRECTION THE MARKS TRAVEL, as they appear on the image: arrows drawn from it at any point must lie along the lines there. It returns `[vx, vy]` in canvas pixels (y down) or an angle in radians — never a scalar that is not that direction (a sideways push, a noise value, an offset, a strength), never one component of it, never an intermediate quantity.
